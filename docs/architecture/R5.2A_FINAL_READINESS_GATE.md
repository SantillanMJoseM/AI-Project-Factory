# R5.2A — Final Implementation Readiness Gate

**Rol:** Revisor independiente de seguridad  
**Fecha:** 2026-11-05  
**Línea base:** `feature/r5.2-workflow-integrity` @ `5bd7187`  
**Entorno:** Debian 13, OpenCode v2.2.5, kernel con user namespaces (`unshare -Urmn` funcional), sin bubblewrap/Docker.

## 1. Resumen ejecutivo

La especificación R5.2A Rev. 1.1 fue declarada **APPROVED_WITH_CONDITIONS**. Este informe evalúa si las condiciones pendientes permiten comenzar la implementación. Se ejecutaron pruebas controladas en directorios desechables bajo `/tmp/r52a-probes/`. **No se modificó código ni documentos del proyecto, no se ejecutaron migraciones sobre la base real y no se usó `--auto`.**

**Veredicto: NOT_READY**

Existen **bloqueos de seguridad** que deben resolverse antes de autorizar cualquier implementación:

1. **Bypass crítico por delegación (`subagent`):** un agente con `bash: deny` pero `subagent: allow` puede ejecutar shell delegando en otro agente. OpenCode implementa `subagent` mediante la clave de permiso `task` y el agente `AG-001` (controller/orchestrator) declara `task: allow`.
2. **El sandbox propuesto es inefectivo con el servidor por defecto:** `opencode run` utiliza un servicio en segundo plano (`opencode serve --service`) que corre en el namespace de montaje del host, por lo que bind mounts, tmpfs y capacidades aplicadas solo al cliente no aíslan nada. Es necesario iniciar un servidor privado dentro del namespace (`--standalone` o `--server`).
3. **La migración 4 del spec no es atómica ni idempotente.** Falla con estado parcial y no inserta la fila `schema_version(4)`. Se demostró que envolverla en `BEGIN IMMEDIATE … COMMIT` + `INSERT INTO schema_version` sí la hace atómica.
4. **Defectos de trazabilidad del plan de pruebas:** AC-024 referencia `TC-001` a `TC-030` que no existen; AC-027 y AC-028 no están definidos en §17; el plan no contiene trazabilidad AC↔prueba; las pruebas unitarias están vacías.
5. **Cuota del modelo agotada:** las pruebas que requieren LLM (`--standalone`, delegación a `general`/`explore`, canary 20×) no se pudieron ejecutar. No se pueden afirmar como verificadas.

Se propone implementación **prohibida** hasta resolver los bloqueos críticos. Una vez resueltos, la implementación de componentes no agente-poderosos (QG, trazabilidad, CLI sin permisos) podría autorizarse por fases.

### 2.6 Otras observaciones críticas

- **`AG-001` (controller) tiene `task: allow`:** en OpenCode la acción `subagent` se controla por la clave `task`. Un agente con `task: allow` puede delegar a `general` y `explore`, que tienen acceso shell. Esto convierte cualquier `bash: deny` en bypassable por delegación.
- **Agentes built-in `general` y `explore` tienen shell allow:** `explore` declara `shell: allow`; `general` hereda `* → allow`. Son agentes reservados de OpenCode y no se pueden modificar directamente, pero sí se puede negar su uso desde el `opencode.json` o mediante el controller.
- **El spec Rev. 1.1 no trata `execute` (Code Mode):** la herramienta `execute` puede realizar solicitudes HTTP aunque `webfetch` esté denegado. En la prueba, `execute`→`fetch` fue bloqueado por `webfetch: deny`, pero esto depende de la implementación de Code Mode y no está especificado.

## 7. Recomendación final

**Veredicto: NOT_READY**

No se autoriza la implementación de R5.2A. Existen **tres bloqueos críticos de seguridad** (B-01 bypass por delegación, B-02 sandbox inefectivo con servidor compartido, B-03 migración no atómica) y dos bloqueos importantes de trazabilidad/cobertura (B-04, B-05).

### 7.1 Implementación limitada: NO AUTORIZADA

Aunque algunos componentes (corrección de `quality_gate.py`, `traceability.py`, CLI sin permisos, tests estáticos) podrían desarrollarse de forma aislada, **no se permite comenzar ninguna implementación** hasta que:

1. Se revise el spec para incorporar controles explícitos sobre `subagent`, `execute` y destinos de delegación.
2. Se rediseñe el sandbox para usar un servidor OpenCode privado dentro del namespace de aislamiento (`unshare -Urmn`).
3. Se corrija la migración 4 para ser atómica e idempotente.
4. Se corrijan los defectos de trazabilidad del plan de pruebas.

### 7.2 Próximos pasos sugeridos

1. **Revisar spec:** añadir §4.3.x sobre restricción de `subagent`/`execute`; corregir §5.2 para servidor privado; rectificar AC-025 (red sí aislable) y AC-027/AC-028.
2. **Revisar plan de pruebas:** eliminar referencias `TC-001`…`TC-030`; añadir mapeo AC↔prueba; definir pruebas unitarias concretas.
3. **Reescribir SQL de migración 4:** transacción explícita + validación previa + `schema_version(4)`.
4. **Reprogramar probes:** cuando se recupere cuota, ejecutar:
   - Delegación a `general`/`explore` desde `AG-001`.
   - Sandbox end-to-end con servidor privado (lectura/escritura confinada).
   - Verificación 20× canary y discovery.
5. **Someter spec revisado a nueva aprobación humana** antes de autorizar implementación.

### 7.3 Distinción importante

Este veredicto autoriza o bloquea **desarrollo**, no operación en producción. Incluso si se desbloquea e implementa R5.2A, el piloto seguirá siendo **READY_WITH_RESTRICTIONS** como máximo, nunca "preparado para producción sin restricciones", dado el aislamiento parcial y la necesidad de supervisión humana.
