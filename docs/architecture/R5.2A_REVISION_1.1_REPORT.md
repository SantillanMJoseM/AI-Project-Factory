## 2. Changes made

### 2.1 Approval flow (§4.4) — revised

**Original (Rev 1.0):** Assumed OpenCode could pause on `ask` in non-interactive mode and wait for human approval.

**Probe 2 result:** OpenCode does NOT pause. It rejects immediately with "This non-interactive run cannot ask the user for permission."

**Revision:** Replaced "pause and wait" with "pre-grant and run":
- Human operator reviews the action before the run starts.
- Operator grants permission via the approval service (bound to project, task, agent, operation, files, expiry, hash).
- Run proceeds with `ask` treated as `deny` by default.
- If a pre-granted approval exists for the specific action, the controller executes the action on behalf of the agent.
- No general authorizations — every approval is scoped.

**New section 7.6** added: "Pre-granted permission model" documenting the full flow and the distinction between human authorization, technical permission, and post-hoc validation.

### 2.2 Sandbox design (§5.2 Layer 4) — revised

**Original (Rev 1.0):** Assumed bubblewrap or Docker available.

**Probe 6 result:** No bubblewrap, no Docker, no Podman. User namespaces work. Read-only bind mounts work. Network namespaces not available. `/proc` mount not available.

**Revision:** Replaced bubblewrap/container with `unshare` + bind mounts:
- `unshare -Urm` for user namespace isolation
- `mount --bind` for read-only factory paths
- `mount -o remount,ro,bind` for read-only enforcement
- `mount --bind` for writable worktree path

**Limitations documented:**
- No network isolation (network namespaces require elevated privileges)
- No independent `/proc` mount
- User namespace maps to nobody (uid 65534)

**Isolation assessment:** Filesystem isolation is enforceable. Network isolation is BLOCKED. Environment allowlist (Layer 3) mitigates secret exposure but not network egress.

**New acceptance criterion AC-025:** Network isolation is BLOCKED (cannot be enforced in this environment).

### 2.3 Worktree materialization (§5.2 Layer 5) — revised

**Probe 7e result:** Worktree without `opencode.json` lacks factory configuration. Only 2 config sources (global + `.opencode/`), no `opencode.json`.

**Revision:** Added materialization requirements:
- `.opencode/agents/` (copied from normative definitions, hash-verified)
- `opencode.json` (factory configuration)
- Verification that materialized files match normative definitions (hash check)

### 2.4 Event schema (§9.3) — added

**Probe 5 result:** Event types observed: `step_start`, `step_finish`, `text`, `tool_use`, `error`. Tool use state has `status`, `input`, `output`, `error`, `metadata`, `time`.

**Addition:** New subsection §9.3 "OpenCode event schema" with:
- Event type table with key fields
- Adapter parsing rules (7 rules)
- Note that delegation events were not observed (unknown schema)

## 3. New document: ADR-R5.2A-SOURCE-OF-TRUTH.md

Created a new ADR documenting the source of truth reconciliation:
- Authoritative source by information type (normative definitions → repository files; operational state → SQLite; evidence → repository files; config → repository files; secrets → environment)
- Reconciliation mechanism (periodic export to `projects/<id>/evidence/<stage>/state_snapshot.json` with SHA-256)
- Divergence detection (compare DB state with last committed snapshot)
- Recovery from divergence (restore from snapshot or export current state)
- Hash chain integrity (prev_hash, row_hash on events and audits)
- Authoritative source decision (operational DB while in progress; repository after stage closure)
- Consequences (new ADR-007, update state-management.md, implement export command, implement hash chain)

Status: Proposed (requires human approval).

## 4. Architectural decisions

1. **Source of truth reconciliation.** SQLite is operational; repository is auditable record. New ADR (ADR-007) required. ADR-001 preserved for normative definitions.
2. **Sandbox technology.** `unshare` + bind mounts instead of bubblewrap/container. Network isolation not available. Filesystem isolation is enforceable.
3. **Approval mechanism.** Pre-granted instead of pause-and-wait. OpenCode does not pause on `ask`. Approvals are scoped to specific task, agent, operation, and file set.
4. **Event parsing strategy.** Parse JSON event stream for tool uses, decisions, errors, session identifiers. Event schema documented from probe evidence.
5. **Worktree configuration.** Materialize `opencode.json` and `.opencode/agents/` with hash verification.
6. **Migration strategy.** Additive only, with pre-migration validation and backup. No rollback (recovery via backup restore).
7. **`deny` enforcement.** Treat as fail-closed (same as `ask` without `--auto`). Controlled probe needed to confirm.

## 5. Limitations

1. **Network isolation not available.** No network namespace (requires elevated privileges). Network egress cannot be restricted via sandbox. Environment allowlist mitigates secret exposure but not network access.
2. **`/proc` mount not available.** No separate process namespace. Process isolation is limited.
3. **User namespace maps to nobody.** Not root. Some operations may fail in the sandbox.
4. **`deny` enforcement not fully verified.** No file was created, but the cause (permission system vs model refusal) is ambiguous.
5. **Event schema for delegation unknown.** No delegation was executed. Task-tool event format must be captured in a probe before R5.4.
6. **20-consecutive-run verification not performed.** Canary and discovery probes were run 1-2 times, not 20.
7. **Migration rollback not supported.** Recovery via backup restore only.
8. **Source of truth ADR is proposed, not approved.** Requires human decision.
