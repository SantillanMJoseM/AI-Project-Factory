### 3.4 Inconsistency: test count mismatch

**Issue:** The test plan's section 2 states "Include positive, negative, adversarial, integration and recovery tests" and the spec's section 16 states "40+ unit, 20+ integration, 15+ adversarial, 10+ security, 5+ recovery, 5+ concurrency" (95+ total). But the test plan header says "30 test cases" while the actual test cases listed (TC-001 through TC-030) total 30, and the additional T-SEC, T-ADV, T-INT, T-REC, T-CONC tests total 48.

**Resolution:** The "30 test cases" in the test plan refers to the core adversarial tests (T-ADV-001 through T-ADV-020 plus T-SEC-001 through T-SEC-008 plus T-INT-001 through T-INT-005). The full suite is 48 tests. The test plan should state "48 test cases" and clarify the breakdown: 13 security + 20 adversarial + 5 integration + 5 recovery + 5 concurrency = 48.

### 3.7 Migration strategy without rollback

**Issue:** The spec proposes additive-only migrations (ALTER TABLE ADD COLUMN, CREATE TABLE IF NOT EXISTS) with no rollback mechanism. If a migration introduces a defect, the only recovery is a new migration.

**Assessment:** This is acceptable for the pilot scale, provided:
1. Every migration is tested on v1, v2, and v3 databases before deployment.
2. A backup is taken before migration (AUD-R5-032).
3. The migration is idempotent (safe to run multiple times).
4. A `schema_version` check prevents running old code on new schemas.

**Risk:** If a migration adds a column with a NOT NULL constraint and no default, existing rows fail. The spec uses `DEFAULT` values for all new columns, mitigating this.

**Recommendation:** Add a pre-migration validation step that checks column compatibility. Add a `migration_test` that runs on a copy of the production database before deployment.

### 4.2 Architectural risks

1. **Sandbox availability.** `unshare` with user namespaces works, but `--map-root-user` failed on `/proc` mount. Bind mounts work in user namespaces. Network namespaces require `-Urn` (user+net+uts). The sandbox design must use `unshare -Urm` with bind mounts, not rely on bubblewrap or Docker.

2. **OpenCode `ask` does not pause.** OpenCode rejects `ask` permissions in non-interactive mode without `--auto`. It does not pause for approval. The approval flow must be pre-granted (human approves before run) or use `--standalone` with a different mechanism. This significantly changes the approval design (§4.4).

3. **Agent discovery from worktree.** Agents load correctly from a worktree with `.opencode/agents/` (18 loaded). But the factory's `opencode.json` is not in the worktree. The worktree needs either a copy of `opencode.json` or a different configuration approach.

4. **Event parsing complexity.** The event stream contains `step_start`, `step_finish`, `text`, `tool_use`. No `error` event type in successful runs; errors appear as `error` type at top level. The adapter must handle both. Tool states have `status: "completed"` or `status: "error"`.

5. **Migration without rollback.** Additive-only migrations are safe but irreversible. A defective migration requires a new migration to fix. This is acceptable if migrations are thoroughly tested.

6. **Source of truth reconciliation.** ADR-001 says repository files are source of truth. The spec proposes SQLite as operational store with periodic export. This requires a new ADR. The current implementation already uses SQLite as the sole source of truth, so this is a documentation change, not an implementation change.

### 4.3 Design defects found

1. **Approval flow assumes pausing.** Section 4.4 assumes OpenCode can pause on `ask` in non-interactive mode. Probe 2 shows it cannot — it rejects immediately. The spec must be revised to use pre-granted approvals or a different mechanism.

2. **Sandbox design assumes bubblewrap/container.** Section 5.2 Layer 4 assumes bubblewrap or Docker. Neither is available. The design must use `unshare` + bind mounts (verified to work).

3. **Worktree needs `opencode.json`.** Section 5.2 Layer 5 creates worktrees but doesn't account for the fact that OpenCode needs `opencode.json` or `.opencode/` in the working directory for agent discovery. The worktree must include a copy of the agent definitions and configuration.

4. **Event parsing not specified.** Section 9.2 requires parsing OpenCode events for tools, decisions, and errors. The spec doesn't specify the exact event schema or how to handle missing fields.

5. **No `deny` enforcement verification.** The spec assumes `deny` permissions are enforced even with `--auto`. This was not tested (AUD-R5-001 probe). Need to verify.

## 6. Architectural decisions requiring approval

1. **Source of truth reconciliation (ADR-007).** ADR-001 says repository files are source of truth; runtime uses SQLite. Spec proposes operational DB + periodic export. This requires a new ADR documenting the reconciliation.

2. **Sandbox technology.** Use `unshare` + bind mounts instead of bubblewrap/container. This is available on the target host (Debian 13).

3. **Approval mechanism.** Since OpenCode does not pause on `ask` in non-interactive mode, approvals must be pre-granted by the human before the run starts. The run proceeds with the permission granted. This changes the flow from "pause and wait" to "pre-approve and run."

4. **Event parsing strategy.** The adapter must parse the JSON event stream to extract tool uses, decisions, errors, and session identifiers. The event schema must be documented.

5. **Worktree configuration.** The worktree must include a copy of `opencode.json` and `.opencode/agents/` for agent discovery. These copies must be verified against the normative definitions.

## 7. Conclusion

The specification is **APPROVED_WITH_CONDITIONS**. The conditions are:

1. **Revise §4.4 (approval flow)** to account for OpenCode's non-pausing behavior. Use pre-granted approvals instead of pause-and-wait.
2. **Revise §5.2 Layer 4 (sandbox)** to use `unshare` + bind mounts instead of bubblewrap/container.
3. **Revise §5.2 Layer 5 (worktree)** to include `opencode.json` and `.opencode/agents/` materialization.
4. **Expand Appendix B** to map all 39 findings.
5. **Fix test count** (48, not 30) and open questions count (7, not 5).
6. **Add event schema specification** in §9.2.
7. **Add probe for `deny` enforcement** (T-SEC-003 already covers this, but it must be verified).
8. **Add pre-migration validation** step in §10.2.
9. **Record new ADR** for source of truth reconciliation.
10. **Verify `deny` enforcement** before implementation (not yet tested).

None of these conditions are blocking — they are refinements that must be applied to the specification before implementation begins. The core architecture and approach are sound.

**Pilot readiness remains NOT_READY** until the implementation is complete and independently re-audited.
