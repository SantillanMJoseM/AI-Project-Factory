# R5.2A — Security & Execution Integrity Technical Specification

## Revision 1.1

This document supersedes Revision 1.0. Changes are documented in `R5.2A_REVISION_1.1_REPORT.md`.

## 1. Executive summary

R5.2A is a specification-only phase that defines the security and execution integrity controls required before any further workflow development. It closes the foundational defects identified in the R5 independent audit (34 findings) and the R5.2 re-audit (5 additional findings, AUD-R5-035 through AUD-R5-039).

The phase targets five critical defects:

1. **AUD-R5-001** — OpenCode `--auto` flag silently approves all `ask` permissions.
2. **AUD-R5-002** — Effective working directory is not isolated (PWD inheritance).
3. **AUD-R5-003** — CLI `task status COMPLETED` bypasses Quality Gate, acceptance and review.
4. **AUD-R5-010** — Concurrent assignment creates duplicate executions (race condition).
5. **AUD-R5-012** — Invalid state transitions bypass the transition table.

The specification preserves the original F0–F5 architecture, all 18 agents, OpenCode native execution, and the R1/R2/R3/R4 remediation history. It does not create a competing agent framework or rewrite agents.

**Key revision (1.1):** Approval flow revised from "pause and wait" to "pre-grant and run" based on probe evidence (OpenCode does not pause on `ask` in non-interactive mode). Sandbox revised from bubblewrap/container to `unshare` + bind mounts (verified available on target host). Worktree materialization now includes `opencode.json`. Event schema specified. Appendix B expanded to all 39 findings.

**Pilot readiness after R5.2A (if all acceptance criteria are met): READY_WITH_RESTRICTIONS.**

## 4. OpenCode permission enforcement design

### 4.1 Problem

The adapter passes `--auto` unconditionally (line 37), auto-approving all `ask` permissions. AG-002 (auditor, `bash: ask`) can execute shell. Developers can modify files without approval.

### 4.2 Required permission model

| Permission | AG-001 | AG-002,003,013-015 | AG-004-007 | AG-008-012 | AG-016,017 | AG-018 |
|---|---|---|---|---|---|---|
| read | allow | allow | allow | allow | allow | allow |
| glob | allow | allow | allow | allow | allow | allow |
| grep | allow | allow | allow | allow | allow | allow |
| bash | ask | ask | deny | ask | ask | deny |
| edit | ask | deny | ask | ask | ask | ask |
| write | ask | deny | ask | ask | ask | ask |
| task | allow | deny | deny | deny | deny | deny |
| webfetch | deny | deny | deny | deny | deny | deny |
| websearch | deny | deny | deny | deny | deny | deny |

### 4.3 Adapter changes required

#### 4.3.1 Remove `--auto`

```python
# BEFORE: cmd = [self.binary, "run", "--agent", agent_id, "--format", "json", "--auto", prompt]
# AFTER:  cmd = [self.binary, "run", "--agent", agent_id, "--format", "json", prompt]
```

Verified: Probe 1 confirms `ask` fails closed without `--auto`.

#### 4.3.2 Permission profile generation

Generate OpenCode permission frontmatter from normative `agents/` definitions. Verify match at startup. Refuse on mismatch.

#### 4.3.3 Permission decision logging

Parse OpenCode JSON event stream for tool uses. Record status (`completed`/`error`), input, output, error, metadata, timing.

#### 4.3.4 Pre-granted approval elevation

Since OpenCode does not pause on `ask` (Probe 2), permissions must be pre-granted:

1. Human operator reviews the requested action before the run.
2. Operator grants the permission via the approval service (bound to project, task, agent, operation, files, expiry).
3. The run proceeds with the permission recorded as granted.
4. The adapter does not pass `--auto`; instead, the agent's effective permission profile is temporarily adjusted for the specific pre-granted action (or the action is executed by the controller on behalf of the agent).

**Alternative (simpler, safer):** Treat `ask` as `deny` in non-interactive mode. The human must explicitly grant permissions before the run. The run fails if an ungranted `ask` is encountered. This is the recommended approach — it requires no permission elevation and is fail-closed.

### 4.4 Human approval model (revised)

**Revision 1.1:** Replaced "pause and wait" with "pre-grant and run."

Authorization is pre-granted by a human operator before execution:

1. **Request:** Agent or controller identifies an action requiring `ask` permission.
2. **Review:** Human operator reviews the action, scope, files, and risk.
3. **Grant:** Operator creates an approval binding: project, task, agent, operation, files, expiry, hash.
4. **Execute:** Run proceeds. If an `ask` permission is encountered, the adapter checks for a matching pre-granted approval. If found, the action is allowed (recorded). If not found, the action is denied (fail-closed).
5. **Consume:** Approval is consumed (single-use) after the action completes.
6. **Audit:** All permission decisions are recorded in execution evidence.

**Distinction:**
- **Human authorization (pre-granted):** A human explicitly approves a specific action before it occurs. Recorded in the approval table with binding hash.
- **Technical permission (OpenCode frontmatter):** The agent's declared permissions (`allow`, `ask`, `deny`). Enforced by OpenCode.
- **Post-hoc validation (controller):** After execution, the controller verifies that all actions were within the pre-granted scope. Mismatches are flagged.

**No general authorizations.** Every approval is scoped to a specific task, agent, operation, and file set. No approval grants blanket shell or write access.

## 5. Filesystem isolation design

### 5.1 Problem

OpenCode resolves working directory from `PWD` environment variable, not process `cwd`. Agent can access files outside the project directory.

### 5.2 Isolation layers

#### Layer 1: Working directory correction

```python
env["PWD"] = str(Path(workdir).resolve())
```

Verified: Probe 3c confirms correct directory reported.

#### Layer 2: Canary verification

Execute a canary probe before each real run. Verify reported directory matches requested. Abort on mismatch.

#### Layer 3: Environment allowlist

```python
ALLOWED_ENV_VARS = {"PATH", "HOME", "LANG", "LC_ALL", "TERM", "USER", "SHELL", "OPENCODE_BIN", "OPENCODE_CONFIG_DIR"}
env = {k: v for k, v in os.environ.items() if k in ALLOWED_ENV_VARS}
env["PWD"] = str(Path(workdir).resolve())
```

#### Layer 4: OS-level sandbox (revised)

**Revision 1.1:** Replaced bubblewrap/container with `unshare` + bind mounts (verified available on Debian 13).

Sandbox construction:
```bash
unshare -Urm /bin/bash -c '
  # Create mount points
  mkdir -p /tmp/scratchpad/sandbox_root
  # Read-only bind: factory normative definitions
  mount --bind /factory/agents /tmp/scratchpad/sandbox_root/agents
  mount -o remount,ro,bind /tmp/scratchpad/sandbox_root/agents
  mount --bind /factory/contracts /tmp/scratchpad/sandbox_root/contracts
  mount -o remount,ro,bind /tmp/scratchpad/sandbox_root/contracts
  # ... (standards, orchestration, .opencode/agents)
  # Writable bind: task worktree
  mount --bind /worktree /tmp/scratchpad/sandbox_root/worktree
  # Run OpenCode inside sandbox
  cd /tmp/scratchpad/sandbox_root/worktree
  PWD=/tmp/scratchpad/sandbox_root/worktree opencode run --agent ... --format json "..."
'
```

**Limitations (verified):**
- No network isolation (network namespaces require elevated privileges).
- No independent `/proc` mount (not available in user namespace).
- User namespace maps to nobody (uid 65534), not root. Read-only bind mounts work. Writable bind mounts work.

**Assessment:** The sandbox provides filesystem isolation (read-only factory, writable worktree only) but does NOT provide network isolation or process isolation. This is **PARTIAL** isolation. The threat model requires:
- ✅ Filesystem: factory read-only, worktree writable, other paths inaccessible
- ❌ Network: not isolated (no network namespace)
- ❌ Process: no separate PID namespace (proc mount not available)

**Conclusion:** The sandbox meets the filesystem isolation requirement but not the network isolation requirement. The acceptance criterion for network isolation (TC-SEC-007, agent cannot read secrets) is achievable via environment allowlist (Layer 3). The acceptance criterion for network egress is **BLOCKED** — cannot be enforced without network namespaces or a proxy.

#### Layer 5: Task worktree

Each task gets an isolated git worktree:
```
/tmp/opencode/worktrees/<project_id>/<task_id>/
```

Worktree materialization includes:
- `.opencode/agents/` (copied from normative definitions, hash-verified)
- `opencode.json` (factory configuration)
- Agent definitions verified against normative source (hash check)

### 5.3 Protected paths

| Path | Access | Enforcement |
|---|---|---|
| `agents/` (normative) | Read-only | Sandbox bind mount (ro) |
| `contracts/` | Read-only | Sandbox bind mount (ro) |
| `standards/` | Read-only | Sandbox bind mount (ro) |

The sandbox provides **partial isolation**:
- ✅ Filesystem: enforced via bind mounts
- ✅ Working directory: enforced via PWD + canary
- ✅ Environment: enforced via allowlist

- ❌ Process: no separate PID namespace

**Acceptance criterion AC-021 (agent cannot read secret env vars): TESTABLE** via environment allowlist.
**Acceptance criterion for network egress: BLOCKED** — cannot be enforced in this environment.

## 6. Task state machine

### 6.1 States

```
PENDING → ASSIGNED → RUNNING → REVIEW_REQUIRED → COMPLETED
Alternative: BLOCKED, REJECTED, FAILED, CANCELLED
```

### 6.2 Valid transitions (authoritative table)

| From | To | Preconditions |
|---|---|---|
| PENDING | ASSIGNED | Dependencies COMPLETED; agent exists |
| ASSIGNED | RUNNING | Dependencies COMPLETED; agent assigned |
| RUNNING | BLOCKED | Any time |
| RUNNING | REVIEW_REQUIRED | Execution completed; outputs recorded |
| RUNNING | COMPLETED | Only via `complete_task()` with QG PASS + acceptance verified |
| RUNNING | FAILED | Execution failed; errors recorded |
| RUNNING | CANCELLED | Reason required |
| BLOCKED | RUNNING | Dependencies resolved; retry_count < max_retries |
| BLOCKED | CANCELLED | Reason required |
| REVIEW_REQUIRED | COMPLETED | Independent review recorded; QG PASS; acceptance verified |
| REVIEW_REQUIRED | REJECTED | Reviewer rejects; reason required |
| REVIEW_REQUIRED | CANCELLED | Reason required |
| REJECTED | RUNNING | Correction assignment recorded |
| REJECTED | CANCELLED | Reason required |
| FAILED | PENDING | Retry allowed; retry_count incremented |
| FAILED | CANCELLED | Reason required |
| Any non-terminal | CANCELLED | Reason required |

### 6.3 Transition engine

One function: `transition(conn, entity_type, entity_id, to, actor, reason, evidence)`.

- Consults the transition table.
- Checks dependencies for ASSIGNED/RUNNING.
- Requires reason for CANCELLED.
- Uses compare-and-set: `UPDATE ... WHERE id=? AND status=?` with `rowcount == 1`.
- Runs in `BEGIN IMMEDIATE` transaction.
- Writes the event in the same transaction.
- No other function may write task status directly.

All callers (CLI, Python API, workflow engine) must use this function. The CLI `task status` command must not accept COMPLETED as a target state.

### 6.4 Concurrency handling

- Every transition uses `BEGIN IMMEDIATE` (SQLite write lock).
- Compare-and-set ensures only one concurrent transition succeeds.
- Failed transitions raise `ConcurrencyError` (not `ValueError`).
- ID generation uses `INTEGER PRIMARY KEY AUTOINCREMENT` (O(1), collision-free).
- Unique partial index on executions: `CREATE UNIQUE INDEX idx_exec_running ON executions(task_id) WHERE status = 'RUNNING'`.

### 6.5 Cancellation

- `CANCELLED` requires a `reason` parameter (non-empty string).
- The reason is stored in the event record.
- No transition to CANCELLED without a reason.

### 6.6 Dependency validation

- `create_task` rejects unknown dependency identifiers.
- `create_task` rejects cyclic dependencies (DFS check).
- Dependencies must be COMPLETED before dependent task can be ASSIGNED or RUNNING.
- `assign_task` checks dependencies before assigning.

### 6.7 Retry limits

- `retry_count` incremented on each FAILED execution.
- `max_retries` default 3 (configurable per task).
- When `retry_count >= max_retries`, task moves to BLOCKED (not FAILED).
- Recovery uses lease-based mechanism: RUNNING executions have a lease (owner PID, heartbeat). Only expired leases are recovered.
- `recover_interrupted` is scoped to a project, not global.

### 6.8 `complete_task` hardening (revised)

`complete_task` must:
1. Require a stored QG result (validated against DB, task_id match, commit match).
2. Require an acceptance verification (validated against DB, task_id match).
3. Reject caller-supplied verdict strings (must reference stored result).
4. Reject boolean `acceptance_verified` (requires verifiable results).
5. Reject arbitrary kwargs as acceptance results (remove `_extract_acceptance_results` fallback).
6. Reject cross-task verification IDs (check `task_id` match).
7. Require outputs and evidence when acceptance criteria exist.

## 7. Authorization model

### 7.1 Operator identity

- Operator identity comes from the OS user (`getpass.getuser()`).
- A repository file (`orchestration/policies/approver-roster.json`) lists authorized human principals.
- Agent identifiers (AG-*) are never accepted as human actors.
- The database file is stored outside the repository working tree (default: `~/.apf/runtime.db` or configurable via `APF_DB_PATH`).
- Database file permissions: 0600 (owner read/write only).

### 7.2 Approval binding

Approvals are bound to:
- `project_id`
- `version`
- `commit` (full SHA)
- `artifact` (path)
- `artifact_hash` (SHA-256)
- `environment`
- `strategy`
- `rollback_plan`
- `risks` (list)

The binding hash is computed over all these fields. Approval verification checks that all fields match the current operation.

### 7.3 Approval enforcement

Gated actions: `release.publish`, `deploy.staging`, `deploy.production`, `data.destructive`, `policy.change`.

For each gated action:
1. Check for an approved, unconsumed approval matching the binding.
2. If none → refuse with `ApprovalRequired`.
3. If found → atomically consume the approval in the same transaction as the state change.
4. If expired → refuse with `ApprovalExpired`.
5. If binding mismatch → refuse with `ApprovalMismatch`.

### 7.4 Single-use enforcement

- `consume_approval` is called within the gated action's transaction.
- After consumption, the approval status is `CONSUMED`.
- A consumed approval cannot be reused.
- Re-consumption raises `ApprovalAlreadyConsumed`.

### 7.5 Approval expiry

- Approvals have an `expires_at` timestamp.
- Expired approvals cannot be consumed.
- Default expiry: 24 hours (configurable).

### 7.6 Pre-granted permission model

Since OpenCode does not pause on `ask` (Probe 2), permissions are pre-granted:

1. **Request:** Controller identifies an action requiring `ask` permission.
2. **Review:** Human operator reviews the action, scope, files, and risk.
3. **Grant:** Operator creates an approval binding (project, task, agent, operation, files, expiry, hash).
4. **Execute:** Run proceeds with `ask` treated as `deny` by default. If a pre-granted approval exists for the specific action, the controller executes the action on behalf of the agent (or elevates the permission for that run).
5. **Consume:** Approval consumed after action completes.
6. **Audit:** All permission decisions recorded in execution evidence.

**No general authorizations.** Every approval is scoped to a specific task, agent, operation, and file set.

## 8. Concurrency and atomicity strategy

### 8.1 Transaction boundaries

Every state-changing operation is wrapped in a single `BEGIN IMMEDIATE` transaction:

```
BEGIN IMMEDIATE;
  -- read current state
  -- validate transition
  -- update state
  -- insert event
  -- insert/modify related records
COMMIT;
```

No intermediate commits. If any step fails, the entire transaction rolls back.

### 8.2 Compare-and-set

```sql
UPDATE tasks SET status = ?, updated_at = ? WHERE task_id = ? AND status = ?;
```

If `rowcount != 1`, raise `ConcurrencyError`.

### 8.3 ID generation

Replace `max+1` scan with `INTEGER PRIMARY KEY AUTOINCREMENT` or a dedicated sequence table updated within the transaction.

### 8.4 Unique constraints

- `CREATE UNIQUE INDEX idx_exec_running ON executions(task_id) WHERE status = 'RUNNING';`
- `CREATE UNIQUE INDEX idx_approval_binding ON approvals(binding_hash) WHERE status IN ('PENDING', 'APPROVED');`

### 8.5 Workflow concurrency

- Workflow runs are scoped to a project.
- `recover_interrupted` is scoped to a project (not global).
- Concurrent workflow runs on the same project are serialized via `BEGIN IMMEDIATE`.

## 9. Evidence and execution record requirements

### 9.1 Evidence envelope

Every evidence file must contain:

```json
{
  "producer": "AG-XXX",
  "session_id": "ses_...",
  "commit": "full 40/64-char SHA",
  "created_at": "ISO-8601 timestamp",
  "inputs_hash": "SHA-256 of inputs",
  "tool": "tool name",
  "tool_version": "version string",
  "content_hash": "SHA-256 of content (computed by controller, not producer)"
}
```

### 9.2 Execution record

Every execution must record:
- `execution_id`, `task_id`, `agent_id`, `started_at`, `status`
- `inputs` (execution brief with objective, acceptance criteria, allowed files, dependencies' outputs)
- `outputs` (agent's outputs)
- `tools_used` (parsed from OpenCode events, not static string)
- `decisions` (parsed from OpenCode events)
- `errors` (from stdout JSON events and stderr)
- `completed_at`
- `commit` (before and after HEAD)
- `changed_files` (git diff --name-status)
- `file_hashes` (SHA-256 of changed files)
- `working_directory` (verified by canary)
- `permission_decisions` (allowed/denied/asked)

### 9.3 OpenCode event schema (new in 1.1)

Events are JSON lines on stdout. Each event has `type` and `part` (or `error`).

**Event types observed:**

| Type | Description | Key fields |
|---|---|---|
| `step_start` | Step begins | `part.id`, `part.sessionID`, `part.messageID` |
| `step_finish` | Step ends | `part.reason`, `part.cost`, `part.tokens` |
| `text` | Assistant text | `part.text` |
| `tool_use` | Tool invocation | `part.tool`, `part.state.status`, `part.state.input`, `part.state.output`, `part.state.error`, `part.state.metadata`, `part.state.time` |
| `error` | Run error | `error.type`, `error.message` |

**Adapter parsing rules:**
1. Any `error` event → run status FAILED or BLOCKED (classify by `error.type`).
2. Any `tool_use` with `state.status == "error"` → record as denied tool; do not fail the run unless the tool was required.
3. `tool_use` with `state.status == "completed"` → record tool name, input, output, timing in `tools_used`.
4. `text` events → concatenate as assistant output.
5. `step_finish` with `reason == "stop"` → run completed.
6. `step_finish` with `reason == "tool-calls"` → more steps expected.
7. Missing `part` or unknown type → log warning, skip.

**Note:** Delegation events (task tool) were not observed. The event schema for delegation is unknown and must be captured in a probe before R5.4.

### 9.4 Audit record

Every audit must record:
- `audit_id`, `project_id`, `scope`, `auditor`, `audited_artifacts`, `findings`, `verdict`, `evidence`, `created_at`
- `executor_agent` (derived from task/execution record, never caller-supplied)
- `independence_verified` (boolean)
- `content_hash` (SHA-256 of audit content)
- `previous_audit_id` (for re-audits)
- `quality_gate_result_id` (link to QG result)
- `prev_hash`, `row_hash` (hash chain)

### 9.5 Audit immutability

- Triggers prevent UPDATE and DELETE on `audits` and `events` tables.
- Hash chain: each event and audit records `prev_hash` and `row_hash`.
- Chain verification command detects tampering.
- Periodic export of chain head to evidence file.

### 10.2 Migration safety (revised in 1.1)

- All migrations are additive (ALTER TABLE ADD COLUMN, CREATE TABLE IF NOT EXISTS).
- Migration version check: `if version < 4`.
- Migration tested on v1, v2, and v3 databases before deployment.
- **Pre-migration validation (new):**
  1. Check current schema version.
  2. Verify database integrity (`PRAGMA integrity_check`).
  3. Create verifiable backup (copy + SHA-256).
  4. Check column compatibility (no conflicting types).
  5. Run migration on a copy first.
  6. Verify post-migration integrity.
  7. Verify all existing tests pass on migrated database.
- **Rollback strategy (new):** No schema rollback. If a migration introduces a defect:
  1. Restore from pre-migration backup.
  2. Fix the migration.
  3. Re-run on a fresh copy.
  4. Document the failure in a decision record.
- Migration is idempotent (safe to run multiple times).

### 10.3 Sequence table for IDs

```sql
CREATE TABLE IF NOT EXISTS id_sequences (
    entity TEXT PRIMARY KEY,
    last_id INTEGER NOT NULL DEFAULT 0
);
```

ID generation:
```python
def next_id(conn, entity, prefix):
    conn.execute("INSERT INTO id_sequences(entity, last_id) VALUES (?, 0) ON CONFLICT(entity) DO NOTHING", (entity,))
    row = conn.execute("SELECT last_id FROM id_sequences WHERE entity=?", (entity,)).fetchone()
    new_id = row[0] + 1
    conn.execute("UPDATE id_sequences SET last_id=? WHERE entity=?", (new_id, entity))
    return f"{prefix}-{new_id:04d}"
```

## 14. Failure handling

### 14.1 Fail-closed defaults

- Missing permission → deny.
- Missing approval → deny.
- Missing evidence → block.
- Unknown state → error.
- Unverified working directory → abort.
- Missing migration → error (do not run on un-migrated DB).

### 14.2 Error reporting

- All errors include: error code, message, entity type, entity ID, timestamp.
- Adapter errors include: stdout (error events), stderr, exit code, command, working directory.
- No silent failures. Every error is logged and returned to the caller.

### 14.3 Recovery

- Interrupted executions: lease-based recovery (only expired leases).
- Failed tasks: retry with limit (max_retries).
- Corrupted database: restore from backup (AUD-R5-032).
- Agent crash: execution marked FAILED, task moves to FAILED, retry allowed.
