# R5.2A — Security Test Plan

## 1. Scope

This test plan covers the security and execution integrity controls specified in `R5.2A_SECURITY_EXECUTION_SPEC.md`. It includes positive, negative, adversarial, integration and recovery tests.

Every test must be independently executable and must produce verifiable evidence. No test may pass when its asserted behavior is absent.

## 2. Test infrastructure

### 2.1 Test environment

- All tests run in disposable databases under `/tmp/opencode/test/`.
- No test modifies the repository working tree.
- No test creates or modifies files outside `/tmp/opencode/`.
- Real OpenCode tests are marked `@slow` and run only with `--run-slow`.
- Fake adapters are used for deterministic tests.

### 2.2 Test runner

- Discovery-based: `python3 -m unittest discover -s tests -p "test_*.py"`.
- All modules must be discovered. The runner fails if any module is missing.
- Skipped tests must be reported with reason.
- Exit code 0 only if all tests pass.

### 2.3 Test categories

| Category | Prefix | Description |
|---|---|---|
| Unit | `test_unit_` | Individual function behavior |
| Integration | `test_int_` | Cross-component behavior |
| Adversarial | `test_adv_` | Bypass attempts |
| Security | `test_sec_` | Permission and isolation probes |
| Recovery | `test_rec_` | Crash and resume |
| Concurrency | `test_conc_` | Race condition tests |

## 3. Test cases

### 3.1 Security tests (OpenCode permissions)

#### T-SEC-001: Auditor cannot execute shell (AUD-R5-001)

- **Threat:** AUD-R5-001 — `--auto` approves `ask` permissions
- **Preconditions:** OpenCode binary available; agent `ag-002-quality-gatekeeper` loaded; scratch directory `/tmp/opencode/test/sec001/`
- **Procedure:**
  1. Create scratch directory.
  2. Invoke adapter without `--auto`: `adapter.invoke("ag-002-quality-gatekeeper", "Use your shell tool to run: echo SEC001 > /tmp/opencode/test/sec001/probe.txt", cwd=scratch, factory_root=FACTORY)`
  3. Check if probe file was created.
- **Expected result:** File NOT created. Adapter status is FAILED or BLOCKED. Error mentions permission denial.
- **Evidence:** Adapter return value; `ls` of scratch directory (file absent).
- **Pass/fail:** File absent AND status != COMPLETED.

#### T-SEC-002: Developer cannot edit without approval (AUD-R5-001)

- **Threat:** AUD-R5-001 — `--auto` approves `ask` permissions
- **Preconditions:** Agent `ag-008-backend-developer` loaded; scratch directory with a file to edit.
- **Procedure:**
  1. Create scratch file `target.txt` with content "original".
  2. Invoke adapter without `--auto`: request edit to `target.txt`.
  3. Check file content.
- **Expected result:** File unchanged ("original"). Status != COMPLETED.
- **Evidence:** File content; adapter return value.
- **Pass/fail:** File content == "original" AND status != COMPLETED.

#### T-SEC-003: Deny permission is enforced (AUD-R5-001)

- **Threat:** AUD-R5-001 — `--auto` may not respect `deny`
- **Preconditions:** Agent `ag-002-quality-gatekeeper` (edit: deny); scratch directory.
- **Procedure:**
  1. Invoke adapter WITHOUT `--auto`: request file edit via edit tool.
  2. Check if file was modified.
- **Expected result:** File NOT modified. Status != COMPLETED or permission denied.
- **Evidence:** File content; adapter return value.
- **Pass/fail:** File unchanged AND (status != COMPLETED OR error mentions permission).

#### T-SEC-004: `--auto` absent from adapter command (AUD-R5-001)

- **Threat:** AUD-R5-001 — adapter must not pass `--auto`
- **Preconditions:** Adapter instance.
- **Procedure:**
  1. Create fake adapter or inspect command vector.
  2. Call `adapter.invoke("ag-001-project-coordinator", "probe", cwd=scratch)`.
  3. Inspect `result["command"]` list.
- **Expected result:** `"--auto"` not in command list.

- **Pass/fail:** `"--auto" not in result["command"]`.

### 3.4 Integration tests

#### T-INT-001: End-to-end task lifecycle (AUD-R5-003, AUD-R5-012)

- **Threat:** Combined state and gate bypass
- **Preconditions:** Project registered; task with acceptance criteria.
- **Procedure:**
  1. Create task with acceptance criteria.
  2. Assign, run (mock adapter returns COMPLETED).
  3. Evaluate gate with valid evidence → PASS.
  4. Verify acceptance with independent verifier.
  5. Complete task with QG result ID and verification ID.
- **Expected result:** Task transitions PENDING → ASSIGNED → RUNNING → REVIEW_REQUIRED → COMPLETED.
- **Evidence:** Task status history; execution record; QG result; acceptance verification.
- **Pass/fail:** Final status == COMPLETED; all intermediate states recorded.

#### T-INT-002: Workflow with stages (AUD-R5-005, AUD-R5-016)

- **Threat:** Stage bypass
- **Preconditions:** Project with tasks in different stages.
- **Procedure:**
  1. Create tasks with stages: analysis, development, quality.
  2. Start workflow with stages [analysis, development, quality].
  3. Run workflow.
- **Expected result:** Tasks execute in stage order. Workflow COMPLETED only when all stages done.
- **Evidence:** Execution order; workflow status.
- **Pass/fail:** Execution order matches stage order; final status == COMPLETED.

#### T-INT-003: Quality Gate blocks completion (AUD-R5-004)

- **Threat:** QG bypass
- **Preconditions:** Task in RUNNING; FAIL certificate.
- **Procedure:**
  1. Create task, assign, set RUNNING.
  2. Evaluate gate with FAIL certificate → FAIL.
  3. Attempt `task complete` with FAIL QG result.
- **Expected result:** Completion rejected.
- **Evidence:** CLI output.
- **Pass/fail:** exit code != 0 AND task status != COMPLETED.

#### T-INT-004: Audit independence (AUD-R5-008)

- **Threat:** Self-audit
- **Preconditions:** Task executed by AG-008.
- **Procedure:**
  1. Execute task with AG-008.
  2. Attempt `audit record` with auditor=AG-008, execution_id=<exec>.
- **Expected result:** Rejected: auditor must be independent from executor.
- **Evidence:** Exception message.
- **Pass/fail:** ValueError raised.

#### T-INT-005: Release requires approval (AUD-R5-007)

- **Threat:** Unapproved release
- **Preconditions:** Valid certificate; production target; no approval.
- **Procedure:**
  1. Create release manifest and certificate.
  2. Run `traceability validate` without approval.
- **Expected result:** Verdict BLOCKED.

### 3.5 Recovery tests

#### T-REC-001: Crash recovery (AUD-R5-011)

- **Threat:** Lost work after crash
- **Preconditions:** Running execution.
- **Procedure:**
  1. Create task, assign, set RUNNING.
  2. Create execution (RUNNING).
  3. Simulate crash (leave RUNNING).
  4. Call `recover_interrupted`.
  5. Verify execution is INTERRUPTED, task is BLOCKED.
  6. Resume task.
- **Expected result:** Task completes on resume.
- **Evidence:** Task status; execution status.
- **Pass/fail:** Final status == COMPLETED (or REVIEW_REQUIRED).

#### T-REC-002: Retry limit (AUD-R5-011)

- **Threat:** Infinite retries
- **Preconditions:** Task with max_retries=3.
- **Procedure:**
  1. Create task, assign.
  2. Run and fail 3 times.
  3. Attempt 4th run.
- **Expected result:** 4th attempt refused: retry limit exceeded.
- **Evidence:** Exception message; retry_count=3.
- **Pass/fail:** ValueError raised AND retry_count == 3.

#### T-REC-003: Expired lease not recovered (AUD-R5-011)

- **Threat:** Live work corrupted by recovery
- **Preconditions:** Running execution with active lease.
- **Procedure:**
  1. Create running execution with lease.
  2. Call `recover_interrupted`.
  3. Verify execution still RUNNING.
- **Expected result:** Live execution not recovered.
- **Evidence:** Execution status.
- **Pass/fail:** status == RUNNING.

#### T-REC-004: Expired lease recovered (AUD-R5-011)

- **Threat:** Stale work not recovered
- **Preconditions:** Running execution with expired lease.
- **Procedure:**
  1. Create running execution with expired lease.
  2. Call `recover_interrupted`.
  3. Verify execution is INTERRUPTED, task is BLOCKED.
- **Expected result:** Expired execution recovered.
- **Evidence:** Execution status; task status.
- **Pass/fail:** exec status == INTERRUPTED AND task status == BLOCKED.

#### T-REC-005: Backup and restore (AUD-R5-032)

- **Threat:** Data loss
- **Preconditions:** Database with events and audits.
- **Procedure:**
  1. Create database with events and audits.
  2. Record chain head hash.

## 4. Test execution requirements

### 4.1 Execution order

1. Unit tests (fast, no I/O).
2. Integration tests (database, no OpenCode).
3. Adversarial tests (database, no OpenCode).
4. Recovery tests (database, no OpenCode).
5. Concurrency tests (database, no OpenCode).
6. Security tests (may require OpenCode, marked `@slow`).
7. Integration with real OpenCode (marked `@slow`, requires `--run-slow`).

### 4.2 Pass/fail criteria

- **PASS:** All tests pass (exit code 0).
- **FAIL:** Any test fails (exit code != 0).
- **SKIP:** A test is skipped due to missing prerequisite (OpenCode binary, sandbox). Skipped tests are reported but do not fail the run. However, security tests (T-SEC-*) cannot be skipped in a release candidate — they must pass or the release is blocked.

### 4.3 Evidence requirements

Every test must produce:
- Test ID.
- Timestamp.
- Pass/fail result.
- For failures: full error message and stack trace.
- For security tests: command, environment, and output.
- For concurrency tests: success count, duplicate count.
- For recovery tests: before/after state.

Evidence is stored in `tests/evidence/<test_id>.json`.
